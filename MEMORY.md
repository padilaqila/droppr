## [2026-09-11] Arsitektur Shared Global Pool + Supabase Realtime & Tab Focus Fallback untuk Feed dan Waitlist
- Apa yang salah: Sebelumnya ketika seorang pengguna menekan tombol sync Telegram di Feed atau Waitlist, hasil sync hanya tersimpan untuk user tersebut (karena RLS `auth.uid() = user_id`), sehingga user lain yang login di perangkat berbeda tidak mendapatkan update data baru dan harus menekan tombol sync sendiri.
- Kenapa terjadi (root cause, bukan cuma gejala): RLS tabel `airdrop_feeds` dan `waitlists` dibatasi eksklusif per `user_id` dengan unique constraint pada `(user_id, source_url)`. Akibatnya terjadi redundansi data duplikat antar user dan tidak ada listener WebSocket Realtime yang menyiarkan data baru ke browser user lain.
- Perbaikan yang dilakukan: (1) Mengubah skema database menjadi Shared Global Pool dengan constraint `source_url` unik untuk katalog sinyal Telegram. (2) Membuka RLS SELECT `airdrop_feeds` untuk seluruh user terautentikasi dan mengisolasi status `is_imported` secara komputasi per-user di client (`syncFeedsWithProjects`). (3) Membagi tabel `waitlists` menjadi katalog discovery publik (`status = 'pending'`) dan registrasi privat (`status = 'joined'` dengan RLS `auth.uid() = user_id`) agar email/wallet user tidak bocor. (4) Memasang Supabase Realtime channel (`postgres_changes`) serta fallback `visibilitychange` di `feed-client-view.tsx` dan `waitlist-client-view.tsx` sehingga pembaruan dari satu user langsung terdistribusi live ke semua user dalam < 1 detik tanpa reload.
- Aturan ke depan: Untuk data bersumber eksternal publik (seperti feed Telegram), selalu gunakan Shared Global Pool dengan RLS terpadu dan pisahkan status personal user ke tabel relasi atau komputasi lokal; pasang listener Realtime yang diimbangi dengan fallback tab visibility change untuk keandalan maksimal.
